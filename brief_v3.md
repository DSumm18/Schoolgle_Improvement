<p><strong>SCHOOLGLE</strong></p><p>Ed AI Platform</p><p>Implementation Brief for Antigravity</p><p>Post-Audit Build Plan: Priorities 1-5</p><p>February 2026 | Version 3.0</p><p>Repository: DSumm18/Schoolgle_Improvement</p><p><strong>This document supersedes all previous comms specs.</strong></p><p><strong>CONFIDENTIAL</strong></p><h1><strong>Executive Summary</strong></h1><p>Schoolgle is an AI-powered operating system for UK schools. The core product is Ed, an AI assistant that helps school staff by performing tasks through natural language conversation. Ed uses a skill-based architecture: discrete, reusable functions that interact with the database, external services, and school systems.</p><p>A codebase audit (February 2026) found the platform is 65% built. The orchestrator framework, specialist personas, estates module, contractor management, and database schema are solid. The critical gaps are: skill invocation relies on regex instead of native LLM function-calling, communication services (SMS/email) are placeholder only, and Ed lacks a knowledge ingestion pipeline for expert-level responses.</p><p>This document defines the five build priorities in order. Each priority unlocks the next. Do not skip ahead.</p><p><strong>▶ The product is not a collection of apps. The product is Ed. Every feature is a skill Ed can use. The UI is one way to access those skills. Ed is the other. Both call the same functions.</strong></p><h2><strong>What Exists (Reuse)</strong></h2><ul><li>EdOrchestrator in packages/ed-agents with intent classification and specialist routing</li><li>Specialist persona prompts: estates, HR, comms, data, governance, send</li><li>Skill registry at apps/platform/src/lib/skills/school-skills-registry.ts with JSON schemas</li><li>Database tables: mc_skills, mc_skill_executions, mc_tools, tool_definitions</li><li>Estates module: full helpdesk ticket lifecycle, contractor management with DBS/accreditation tracking</li><li>Reminder service with scheduling logic (needs wiring to real providers)</li><li>Two Ed deployments started: apps/ed-parent (public) and apps/ed-staff (internal)</li><li>Context awareness: Ed can read current page URL, title, visible content</li><li>TTS via Microsoft Cognitive Services (to be replaced with Fish Audio)</li></ul><h2><strong>What Needs Building (Gaps)</strong></h2><ul><li>Native LLM function-calling to replace regex skill detection in skills-agent.ts</li><li>Live communication providers: Twilio (SMS/voice), email service, Fish Audio (TTS)</li><li>Knowledge ingestion pipeline: vector store or managed knowledge base for expert responses</li><li>Context-aware Ed behaviour: proactive help based on current page and user role</li><li>Human-in-the-loop approval UI for high-risk skill executions</li><li>Communication skills: contractor chasing, gate access, cascades, alerts</li><li>Credit/billing system for SMS spend control</li></ul><h1><strong>Priority 1: Fix Skill Invocation (Native Function-Calling)</strong></h1><p><strong>▶ This is the foundation. Nothing else works properly until this is done.</strong></p><h2><strong>Problem</strong></h2><p>Currently, skills-agent.ts uses regex and keyword matching to detect when a user wants to invoke a skill. This means Ed can only recognise skills if the user phrases their request in specific ways. Natural conversation breaks it. The leaky tap example ('I just fixed that tap in the boys toilet, ticket sorted') would not be matched by regex looking for 'update helpdesk ticket'.</p><h2><strong>Solution</strong></h2><p>Replace regex detection with native LLM function-calling (also called tool-use). The AI model receives a list of available skills as structured tool definitions. When the user's message implies a skill should be called, the model returns a tool_call with the skill name and parameters extracted from natural language. This is how OpenAI, Anthropic, and Google models are designed to work.</p><h2><strong>Implementation</strong></h2><ol><li>Refactor skills-agent.ts to build a tools array from the existing school-skills-registry.ts</li><li>Each skill's JSON schema becomes a tool definition passed to the LLM</li><li>When the LLM returns a tool_call, the orchestrator routes to the correct handler</li><li>Log every invocation to mc_skill_executions (this already exists)</li><li>If the skill requires confirmation (e.g., closing a ticket, sending SMS), return a confirmation prompt before executing</li></ol><h2><strong>Model Considerations</strong></h2><p>The system uses OpenRouter. Confirm that the target model supports function-calling natively. Gemini 2.0 Flash supports it and is cost-effective. GPT-4o supports it. If the current model doesn't support tool-use, switch to one that does. This is non-negotiable for the architecture to work.</p><h2><strong>Files to Modify</strong></h2><ul><li>packages/ed-agents/src/agents/skills-agent.ts - replace regex with tool definitions</li><li>packages/ed-agents/src/orchestrator/orchestrator.ts - handle tool_call responses</li><li>apps/platform/src/lib/skills/school-skills-registry.ts - ensure all skills have valid JSON schemas</li><li>apps/platform/src/app/api/skills/invoke/route.ts - ensure it handles orchestrator-driven calls</li></ul><h2><strong>Test Criteria</strong></h2><p>Ed must correctly identify and call the right skill from all of these natural language inputs:</p><ul><li>'Can you log a helpdesk ticket? Schools get pressured by contractors into unnecessary work. A contractor says 'you really need to replace this entire system' when a repair would suffice. A fire safety company says 'you must upgrade all your doors' when the current doors are compliant. Schools spend thousands on work they don't need because they can't distinguish statutory requirements from upselling.</p><p>Ed must be able to:</p><ul><li>When a contractor recommends work, Ed should be able to check: is this work required by statute? What does the current compliance status show? When was the last inspection and what did it find?</li><li>Provide a clear assessment: 'This is a statutory requirement, you must do this' OR 'This is recommended best practice but not legally required' OR 'Your current setup is compliant. This would be an improvement but is not necessary for compliance.'</li><li>Cite the specific regulation or standard that applies</li><li>Suggest what would actually be sufficient to remain compliant vs the gold-plated option the contractor is selling</li><li>Flag the risk level: 'If you don't do this, the risk is [X]. The likelihood is [Y]. Your current mitigation is [Z].'</li></ul><p><strong>Example interaction:</strong></p><p>Staff: 'The fire safety company says we need to replace all our fire doors.</p><p>       They quoted us twelve grand.'</p><p>Ed: 'Let me check your records. Your doors are FD30S rated and still within</p><p>     their service life.</p><p>     My assessment: Replacing the seals on 3 doors would restore compliance.</p><p>     Full replacement is not required by statute and was not recommended by</p><p>     your fire risk assessor.
